Start here

Use the system in the right order

The safest daily flow is resident-first: save the resident, pair the device, send display text, send photo when needed, and check logs.

01

Confirm network

Connect the laptop to the facility network or approved VPN before login. If the control service is unreachable, do not edit resident data.

02

Save resident record

Enter name, room, diet, texture, fluids, note, drinks, source document, safety review, and resident photo.

03

Pair display device

Select one resident and one online ESP32 display unit. Pairing automatically prepares that device for updates.

04

Send display updates

Save sends the e-paper text. Use the resident photo button when the LCD picture needs to be pushed separately.

05

Schedule LCD sleep

IT Admin or authorised users can set global LCD on/off schedule entries. Multiple schedule entries may be used.

06

Verify and audit

Verifier confirms software data matches the physical e-paper. Admin reviews change requests and resident audit history.

Role manuals

Choose the guide for your responsibility

IT

IT Admin

Owns technical health, control service, users, backups, firmware, device provisioning, battery policy, and system recovery.

  • Create and deactivate users.
  • Set temporary passwords and enforce password change.
  • Configure Google Drive backup, SMTP alerts, OTA firmware, and operation manager.
  • Troubleshoot Raspberry Pi, network, ESP32, LCD, e-paper, and download site issues.
AD

Admin / Nurse Admin

Owns resident accuracy and approval. Admin can create or edit residents and approve staff change requests.

  • Create resident records with source documents.
  • Review staff comments before pushing changes.
  • Check resident audit history and attached proof documents.
  • Keep resident photo, diet, texture, fluids, notes, and drinks current.
ST

Staff / Nurse

Views resident information and submits comments or requested updates for Admin approval.

  • Search residents and confirm current display information.
  • Submit a resident change request with a clear reason.
  • Do not directly change live display data unless given Admin access.
  • Report device or screen concerns with room, resident, and device ID.
VF

Verifier

Checks that the software resident record matches what is physically shown on the e-paper display.

  • Select the resident or unit assigned for checking.
  • Compare name, room, diet, texture, fluids, note, and drinks.
  • Mark verified when correct, or mismatch when not correct.
  • Escalate mismatch to Admin and IT Admin if the device did not update.

  6. After pairing, the latest resident text is prepared for the display pipeline.

  2. Attach the resident photo if it is missing or wrong.
  3. Use Send Resident Photo when the LCD image needs to be pushed separately.
  4. Wait for the success response before sending another photo.
  5. If the LCD turns white but updates after device reboot, use the LCD/photo troubleshooting guide.

Troubleshooting

Common issues and what to do first

Start with simple checks before assuming a hardware failure. Capture exact error text, device ID, time, room, and user role.

Cannot log in

Likely cause: laptop is not on the facility network/VPN, server is unreachable, or credentials are wrong.

  1. Connect to the dedicated facility network or approved VPN.
  2. Ask IT Admin to confirm the Control Service is online.
  3. If password was reset, use the temporary password and change it after login.

ESP32 shows offline

Likely cause: device WiFi is down, Pi gateway unreachable, TCP connection dropped, or firmware not reconnecting.

  1. Confirm the device has power and the correct WiFi credentials.
  2. Check IT Admin device list for last seen time and IP.
  3. Use USB provisioning if WiFi credentials changed.
  4. Restart the display unit only after network checks are done.

LCD photo turns white

Likely cause: LCD bus reclaim, image orientation, or firmware/display refresh path.

  1. Do not send text and photo repeatedly at the same time.
  2. Send photo once and wait for acknowledgement.
  3. Confirm the firmware version includes the shared-bus LCD refresh fix.
  4. If it only appears after reboot, escalate to IT Admin with firmware version and device ID.

E-paper looks dirty or partial

Likely cause: incomplete refresh, old content not fully wiped, busy pin timing, or wrong display driver sequence.

  1. Wait for the e-paper update to finish before sending another update.
  2. Confirm the firmware performs a full clear before drawing resident text.
  3. Check battery/power stability.
  4. Capture a photo and serial logs for IT Admin.

Google Drive backup fails

Likely cause: Drive token missing, rclone remote missing, bad folder target, or internet unavailable.

  1. Open IT Admin Settings, then Integrations.
  2. Confirm Google Drive target, OAuth token or service account, and Test Drive status.
  3. Create Backup still saves locally even if cloud upload fails.

Download page unreachable

Likely cause: wrong network, download-site service stopped, firewall, or wrong hostname.

  1. Use the Pi IP address first, then hostname after it works.
  2. Check the download service status on the Pi.
  3. Confirm port 8090 for installer downloads and port 8092 for this support portal.

Important recovery note

The backup is a Whisperwood recovery bundle, not a bootable SD-card image. It restores the application database, documents, resident images, schedule/cache files, firmware files, and key service configuration after a replacement Pi has been prepared.

Technical section

For IT Admin and implementation engineers

Core services

Desktop app
Resident records, role access, pairing, LCD schedule, logs, backups, firmware tools.
Control Service
Authentication, residents, devices, schedules, backup/restore, integrations, firmware releases.
Operation Manager
ESP32 gateway, TCP device communication, LCD commands, image processing, OTA handoff.
ESP32 firmware
WiFi reconnect, resident text rendering, LCD image receive, battery telemetry, OTA firmware.

Device communication chain

  1. Desktop saves resident record to server database.
  2. Control Service builds resident display payload.
  3. Operation Manager sends text or image to paired ESP32.
  4. ESP32 updates e-paper or LCD and returns ACK.
  5. Control Service logs success or failure for review.
